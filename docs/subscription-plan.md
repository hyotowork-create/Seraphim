# 교회학교 설교·자료 제작 도구 — 구독형 서비스 전환 기획안

> 작성일: 2026-06-22
> 대상 산출물: 현재의 단일 파일 도구(`tools/tool-v6.html`)를 유료 구독 SaaS로 전환

---

## 0. 한 줄 요약

지금은 **"사용자가 자기 API 키를 넣어 직접 돌리는 무료 HTML 파일"**이라 돈을 받을
방법이 없습니다. 구독료를 받으려면 **"우리 서버가 AI 호출을 대신 해주고, 로그인·결제·
사용량 제한을 거는 웹 서비스"**로 구조를 바꿔야 합니다. 이 문서는 그 전환 방법과
가격·일정·비용·리스크를 정리한 것입니다.

---

## 1. 현재 구조의 한계 (왜 지금은 과금이 불가능한가)

| 항목 | 현재 상태 |
|---|---|
| 실행 방식 | 정적 HTML 파일을 PC에서 더블클릭 (서버 없음) |
| AI 호출 | 사용자가 **본인 Gemini API 키**를 입력해 브라우저에서 직접 호출 (BYOK) |
| 비용 부담 | 100% 사용자 (우리는 비용 0, 수익도 0) |
| 복제 | 파일만 있으면 누구나 무한 복사·공유 가능 |
| 로그인/결제/사용량 제한 | 전부 없음 |

→ **결론: 파일 자체로는 절대 과금할 수 없다.** 가치를 "파일"이 아니라 "서비스 접근권"에
실어야 한다.

---

## 2. 무엇을 팔 것인가 — 3가지 패키징 모델

### 모델 A. 자체 호스팅 + 사용량 과금 ★권장
- 사용자는 API 키를 모름. 우리가 키를 보유하고 AI를 대신 호출.
- 월 구독료에 "기획 N회 / 이미지 N장 / 주보·공과 무제한" 같은 한도 포함.
- **장점:** 가장 자연스러운 구독 경험, 진입장벽 최저(키 발급 불필요).
- **단점:** AI 비용을 우리가 선부담 → 가격 설계와 사용량 제한이 생명.

### 모델 B. BYOK + 라이선스 키
- 사용자가 자기 키는 그대로 쓰되, 도구 사용권에 월정액 부과.
- **장점:** 우리 AI 비용 부담 없음.
- **단점:** "키도 내가 넣는데 왜 월정액?" 저항감. 라이선스 우회도 상대적으로 쉬움.

### 모델 C. 교회/교단 단위 라이선스
- 개인이 아니라 "교회" 단위 연간 계약 (교사 여러 명 공유).
- **장점:** 교회는 기관 계약에 익숙, 객단가(ARPU) 높음.
- **단점:** 영업 사이클 길고 의사결정자 설득 필요.

> **추천 조합: A(개인 월구독) + C(교회 묶음)**
> 개인 교사용 월정액으로 시작하되, 교회 전체 묶음 할인 플랜을 함께 제공.

## 3. 가격안 (참고용 — 실제는 4번 비용 검증 후 확정)

| 플랜 | 가격(월) | 포함 내용 |
|---|---|---|
| 무료 체험 | 0원 | 가입 시 기획 1회 + 이미지 프롬프트 1세트(16장) |
| 개인 | 9,900~14,900원 | 부서 5종 무제한 전환, 기획 월 10회, 주보·공과 무제한, 이미지 프롬프트/PPTX 무제한 |
| 교회 | 49,000~79,000원 | 교사 계정 5개, 부서별 사용 통계, 우선 지원 |

- **이미지 실제 생성(Nano Banana)**은 토큰 단가가 커서 **크레딧제** 권장
  (예: 월 100장 포함, 초과분 건당 과금). 프롬프트 텍스트 생성과 이미지 생성을 분리 과금.
- 연 결제 시 2개월 할인(흔한 SaaS 관행) 등으로 이탈 방지.

## 4. 비용 구조 — 반드시 먼저 계산할 것

구독가를 정하기 전에 **"사용자 1명이 한 달에 우리에게 얼마의 AI 비용을 발생시키는가"**를
실측해야 합니다.

- 기획 1회 ≈ 입력 300 + 출력 3,000 토큰 수준 (이번 테스트 실측: 합계 약 5,200토큰)
- 이미지 1장(Nano Banana)은 텍스트보다 **단가가 훨씬 높음** → 여기가 적자 포인트
- **권장 작업:**
  1. 플랜별 "예상 월 사용량 × 모델 단가"로 1인당 원가 산출
  2. 원가 + 결제 수수료(약 3%) + 마진을 얹어 구독가 결정
  3. 한도(rate limit)를 반드시 걸어 헤비 유저로 인한 적자 차단

## 5. 기술 전환 — 새로 만들어야 하는 것

지금 UI와 프롬프트 빌더 로직(`buildSysPlan` 등)은 거의 그대로 재사용 가능합니다.
바꿔야 하는 건 **"브라우저가 직접 Gemini를 호출"하던 부분을 "우리 서버 경유"로** 바꾸는 것.

| 영역 | 현재 | 전환 후 |
|---|---|---|
| API 키 | 사용자 입력 | **서버 환경변수로 보관**, 클라이언트엔 절대 노출 안 함 |
| 백엔드 | 없음 | API 대리 호출 서버 (Node/Express 또는 Cloudflare Workers / Vercel Functions) |
| 인증 | 없음 | 이메일 또는 **카카오 로그인** (국내 교회 사용자 친화적) |
| 결제 | 없음 | **PortO ne(아임포트) / 토스페이먼츠 / 카카오페이** 정기결제 연동 |
| 사용량 미터링 | 없음 | 호출 횟수·토큰 카운트 → 플랜 한도 초과 시 차단/추가과금 |
| 데이터 저장 | 브라우저 메모리 | DB(PostgreSQL/Supabase 등)에 사용자·구독·생성 이력 저장 |
| 호스팅 | 로컬 파일 | 웹 배포 + 도메인 (Vercel / Cloudflare Pages) |

> 핵심 보안 원칙: **API 키는 절대 프런트엔드로 내려보내지 않는다.** 모든 AI 호출은
> 로그인·구독 상태를 검증한 뒤 서버에서만 실행.

### 추천 스택(가벼운 시작 기준)
- 프런트: 기존 HTML/JS 거의 재사용 (호출부만 `/api/...`로 교체)
- 백엔드: Vercel Serverless Functions 또는 Cloudflare Workers
- DB/인증: Supabase (Postgres + Auth 한 번에)
- 결제: 국내라면 PortOne(구 아임포트)로 카드 정기결제 + 카카오페이

## 6. 법적·정책 검토 (착수 전 필수 확인)

1. **Google Gemini API 약관** — AI 결과물을 유료 서비스로 제공하는 건 보통 OK지만,
   "API 접근권 자체의 재판매/키 전대"는 금지일 수 있음. → Google AI 약관/Cloud 영업
   확인 필요.
2. **성경 본문 저작권** — 개역개정 등 한국어 번역본은 재단/출판사 저작권. 자동 대량
   출력·배포 시 사용 허락 확인.
3. **AI 생성 이미지 상업적 이용권** — Nano Banana 생성물 상업 사용 약관 확인.
4. **개인정보보호(PIPA)** — 회원/결제 정보 처리방침, 결제정보는 PG사 위탁.
5. **사업자/통신판매업 신고·전자상거래법** — 국내 유료 서비스 운영 시 필요.

## 7. 단계별 로드맵

| 단계 | 핵심 작업 | 산출물 |
|---|---|---|
| 0. 검증 | 비용 실측, 약관 검토, 타깃 교사 5~10명 인터뷰("월 얼마면 쓸까") | 가격 가설, 시장성 판단 |
| 1. MVP | 로그인 + 서버 대리호출 + 무료 1회 + 결제 1개 플랜 | 과금 가능한 최소 웹앱 |
| 2. 베타 | 실제 교사 대상 유료 베타, 사용량/이탈 데이터 수집 | 가격·한도 조정 근거 |
| 3. 정식 | 교회 플랜 추가, 통계·이력, 결제 자동화 안정화 | 정식 출시 |
| 4. 확장 | 부서별 템플릿 마켓, 타 교단 콘텐츠, 추천/제휴 | 매출 확대 |

## 8. 가장 빠른 검증 경로 (돈/시간 아끼는 법)

전체 SaaS를 만들기 전에, **유료 의사를 먼저 검증**하길 강력 권장:

1. 지금 도구를 그대로 두되, **수동 운영형 베타**로 시작
   - 예: 신청 폼 → 입금 확인 → 사용 안내(BYOK 가이드 + 도구 전달)
   - "정말 돈 내고 쓸 사람이 있는가"를 코드 없이 먼저 확인
2. 신청자가 모이면 → 그때 모델 A(자체 호스팅) 백엔드 개발 착수
3. 이렇게 하면 **시장성 없는데 큰 개발비 쓰는 리스크**를 피할 수 있음
